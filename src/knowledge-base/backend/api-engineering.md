# 接口设计与后端工程化

全栈开发的核心能力不是“前端也写一点后端”，而是能把需求拆成页面、接口、数据、权限、部署和排障链路，并且知道每一层的边界。

## 接口设计清单

| 项目 | 说明 |
| --- | --- |
| URL | 资源语义清晰，例如 `/api/articles/{id}` |
| Method | 查询用 GET，新增用 POST，更新用 PUT/PATCH，删除用 DELETE |
| 入参 | 使用明确 DTO，字段必填、长度、类型要清楚 |
| 出参 | 统一响应结构，包含 `code`、`message`、`data` |
| 错误码 | 区分登录失效、无权限、参数错误、业务失败 |
| 权限 | 明确是否需要登录、角色、资源归属校验 |
| 日志 | 关键接口记录用户、参数摘要、耗时、异常 |
| 幂等 | 支付、提交、兑换、审核等接口避免重复执行 |

## 统一响应结构

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "id": 10001
  }
}
```

前端配合方式：

- `code === 0` 正常渲染业务数据。
- 登录失效统一跳转登录。
- 无权限展示提示或隐藏操作入口。
- 参数错误回显到表单项。
- 业务失败展示明确提示，避免只显示“请求失败”。

## 典型业务接口拆解

以文章审核为例：

1. 列表接口：支持标题、作者、状态、时间范围筛选。
2. 详情接口：展示文章内容、作者信息、历史审核记录。
3. 审核接口：提交通过或拒绝，写入审核意见。
4. 日志接口：展示操作人、操作时间、状态变化。
5. 权限控制：只有审核角色可以操作。

这个拆解能让前端页面结构、后端接口、数据库表结构保持一致，减少联调时的反复沟通。

## 联调流程

```text
产品需求
  -> 页面原型
  -> 接口字段
  -> Mock 数据
  -> 前端页面
  -> 后端接口
  -> 联调
  -> 测试
  -> 发布
```

高效联调的关键：

- 接口文档提前约定字段、枚举和错误码。
- 前端先用 Mock 数据完成页面状态。
- 后端接口完成后对照文档验字段。
- 异常场景要覆盖，例如空数据、无权限、重复提交。
- 发布前确认环境变量、代理、跨域和接口域名。

## 部署与排障

常见问题定位顺序：

1. 页面是否加载成功，静态资源是否 404。
2. 接口域名和代理是否正确。
3. 请求参数是否符合后端约定。
4. 服务端日志是否有异常。
5. 数据库是否有慢查询或数据状态异常。
6. Nginx、网关、跨域、证书是否影响访问。

全栈开发需要能看懂这些信号。即使不是每一层都由自己负责，也能快速把问题定位到正确的人和正确的模块。
